#001
연관 엔티티 고유값을 파생 필드로 저장하는 방식의 문제 (post.writer, comment.writer)
설계 리팩터링 JPA
▼
// 문제

Post.writer, Comment.writer 필드에 Member.email을 직접 복사해 저장하는 방식을 사용했다. 이는 동일한 정보가 두 테이블에 중복 저장되는 데이터 정규화 위반이다. 회원이 이메일을 변경하면 Post, Comment 등 관련된 모든 테이블의 writer 필드를 일괄 업데이트해야 하는 동기화 문제가 생긴다. 

// 문제가 있는 구조
// Member 테이블:  id=1, email=hong@test.com
// Post 테이블:    id=1, writer="hong@test.com", member_id=1
// → 같은 정보가 두 군데 저장됨

@Entity
public class Post {
    private String writer;   // member.email 복사 저장 ← 문제

    @ManyToOne(fetch = LAZY)
    private Member member;   // 같은 정보를 연관관계로도 보유
}
// 해결 방향

파생 필드를 제거하고 연관관계에서 직접 꺼내는 방식으로 변경한다. v1에서는 Object Reference, v2(shop-v2)에서는 ID Reference로 전환하며 완전히 정리한다. 

// v1 — Object Reference에서 직접 접근
post.getMember().getNickname()
post.getMember().getEmail()

// v2 — ID Reference (shop-v2 리팩터링 목표)
public class Post {
    private Long memberId;   // FK만 저장, 객체 참조 없음
    // 필요 시 MemberService.findById(memberId)로 명시적 조회
}
// 배운 점

편의를 위해 파생 필드를 추가하는 것은 단기적으로는 join을 줄여주지만, 데이터 정합성 문제와 동기화 비용이라는 기술 부채를 낳는다.

실무에서도 이러한 이유로 Object Reference(v1) → ID Reference(v2, MSA 대응) 방향으로 설계를 발전시킨다. ID Reference는 Aggregate 경계를 명확히 하고 영속성 컨텍스트 의존도를 낮추는 DDD 원칙과도 일치한다.

#002
Page<T> Redis 캐싱 시 직렬화 문제 — PageImpl + LocalDateTime 역직렬화 실패
성능 설계
▼
// 문제

게시글 목록 조회 결과(Page<PostListDto>)를 @Cacheable로 Redis에 캐싱하려 했으나 두 가지 직렬화 오류가 연속으로 발생했다. 

// 오류 1 — PageImpl 역직렬화 실패
// PageImpl에 기본 생성자가 없어 Jackson이 JSON → 객체 변환 불가
Cannot construct instance of `org.springframework.data.domain.PageImpl`
(no Creators, like default constructor, exist)

// 오류 2 — LocalDateTime 직렬화 실패
// PostListDto.createTime 필드가 LocalDateTime 타입
Java 8 date/time type `java.time.LocalDateTime` not supported by default:
add Module "com.fasterxml.jackson.datatype:jackson-datatype-jsr310"
// 시도한 해결 방향

오류 1 해결을 위해 CachePage<T> 커스텀 DTO를 도입했고, 오류 2 해결을 위해 CacheConfig에 JavaTimeModule을 등록한 커스텀 ObjectMapper를 적용하려 했다. 그러나 우회책이 쌓일수록 코드 복잡도가 급격히 증가했다. 

// 시도 1 — CachePage 커스텀 DTO
public class CachePage<T> implements Serializable {
    private List<T> content;
    private int pageNumber, pageSize, totalPages;
    private long totalElements;
}

// 시도 2 — CacheConfig에 JavaTimeModule 등록
ObjectMapper objectMapper = new ObjectMapper();
objectMapper.registerModule(new JavaTimeModule());
objectMapper.disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS);
objectMapper.activateDefaultTyping(..., DefaultTyping.NON_FINAL);
// 최종 결정 — 목록 캐싱 제거

우회책을 계속 쌓는 것보다 목록 캐싱 자체를 포기하는 것이 합리적이라 판단했다. Write-behind 패턴(조회수 캐싱)은 유지하고, 게시글 목록 캐싱은 제거했다. 

// 제거 — @Cacheable, @CacheEvict, CachePage, CacheConfig 복잡도
// 유지 — Write-behind 조회수 캐싱 (StringRedisTemplate + @Scheduled)

@Transactional(readOnly = true)
public Page<PostListDto> searchPosts(PostSearchConditionDto cond, Pageable pageable) {
    return postRepository.searchPosts(cond, pageable); // 단순 DB 조회
}
// 배운 점

Page<T>처럼 Spring 내부 클래스를 Redis에 캐싱하는 것은 생각보다 많은 설정이 필요하다. PageImpl은 기본 생성자가 없고, LocalDateTime은 별도 모듈 등록이 필요하며, 제네릭 타입 정보 보존을 위해 DefaultTyping 설정까지 필요하다.

캐싱 도입 전에 "직렬화 가능한 타입인가"를 먼저 검토해야 한다. 단순 String/Long 값(조회수 카운터)은 캐싱이 쉽지만, 복잡한 객체 그래프는 캐싱 비용이 기대보다 훨씬 클 수 있다.

과설계를 인식하고 단순한 방향으로 롤백하는 결정 자체도 중요한 엔지니어링 판단이다.

#003
낙관적 락 + @Retryable 고부하 환경 이슈 — StockNotEnoughException 재시도 진입, MySQL 데드락, H2 vs MySQL 성능 차이, 비관적 락 비교
성능 버그
▼
// 문제 1 — StockNotEnoughException이 @Retryable 내부로 진입

@Retryable(retryFor = ObjectOptimisticLockingFailureException.class)로 설정했음에도 StockNotEnoughException 발생 시 @Recover 메서드를 찾으려는 동작이 발생했다. spring-retry는 retryFor에 없는 예외도 @Recover 탐색을 시도하며, 해당 예외 타입에 맞는 @Recover가 없으면 ExhaustedRetryException을 던져 500이 된다. 

// 증상
ExhaustedRetryException: Cannot locate recovery method
Caused by: StockNotEnoughException: 재고가 부족합니다.

// 해결 1 — noRetryFor로 명시적 제외
@Retryable(
    retryFor = {ObjectOptimisticLockingFailureException.class},
    noRetryFor = {StockNotEnoughException.class, ItemNotFoundException.class},
    maxAttempts = 5,
    backoff = @Backoff(delay = 100)
)

// 해결 2 — @Recover를 RuntimeException으로 범용화
@Recover
public OrderDetailDto recoverCreateOrder(RuntimeException e, ...) {
    if (e instanceof ObjectOptimisticLockingFailureException
            || e instanceof CannotAcquireLockException) {
        throw new OptimisticLockingFailureException("요청 충돌이 발생하였습니다.");
    }
    throw e; // StockNotEnoughException 등은 그대로 re-throw
}
// 문제 2 — MySQL InnoDB 데드락 발생

@Version 낙관적 락을 적용했음에도 50명 동시 요청 시 MySQL에서 데드락이 발생했다. 낙관적 락은 커밋 시점에 version 불일치를 감지하는 방식이라, 그 이전에 InnoDB 행 잠금(row lock) 경합이 먼저 발생하면 DB 레벨 데드락을 막지 못한다. H2는 InnoDB의 갭 락·넥스트 키 락 같은 복잡한 잠금 메커니즘이 없어 데드락이 발생하지 않는다. 

// MySQL 데드락 에러
CannotAcquireLockException: Deadlock found when trying to get lock
  update item set ... version=? where id=? and version=?

// 해결 — CannotAcquireLockException도 재시도 대상에 추가
@Retryable(
    retryFor = {ObjectOptimisticLockingFailureException.class,
                CannotAcquireLockException.class},
    ...
)

// GlobalExceptionHandler에도 추가
@ExceptionHandler({OptimisticLockingFailureException.class,
                    CannotAcquireLockException.class})
public ResponseEntity handleLockException(Exception e) {
    return ResponseEntity.status(HttpStatus.CONFLICT)
            .body(ApiResponse.error(e.getMessage()));
}
// 비교 실험 — 낙관적 락 vs 비관적 락 (k6, 50 VUs, 10s)

낙관적 락의 MySQL 데드락 문제를 확인한 후 비관적 락(SELECT FOR UPDATE)을 적용하고 동일 조건으로 부하 테스트를 진행해 트레이드오프를 측정했다. 

// 비관적 락 적용 방법
// ItemRepository
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT i FROM Item i WHERE i.id = :id")
Optional<Item> findByIdWithLock(@Param("id") Long id);

// OrderService — findById → findByIdWithLock 교체
Item item = itemRepository.findByIdWithLock(id)
        .orElseThrow(() -> new ItemNotFoundException(id));

// 결과 비교표
// ┌──────────────────┬──────────┬────────────────┬────────────────┬──────────┐
// │                  │ 락 없음  │ 낙관적락 (H2)  │ 낙관적락 (MySQL)│ 비관적락 │
// ├──────────────────┼──────────┼────────────────┼────────────────┼──────────┤
// │ 성공률 (201)     │   21%    │      93%       │      63%       │   56%*   │
// │ 충돌/오류 (409)  │ 500 데드락│      6%        │      36%       │    0%    │
// │ 응답시간 (avg)   │   빠름   │     2~3ms      │     2~3ms      │   70ms   │
// │ 데이터 정합성    │  미보장  │      보장       │      보장       │   보장   │
// │ 데드락 발생      │   있음   │      없음       │      있음       │   없음   │
// └──────────────────┴──────────┴────────────────┴────────────────┴──────────┘
// * 재고 소진으로 인한 400 포함
// 배운 점

낙관적 락은 충돌이 드문 환경에 적합하다. 재고 차감처럼 동일 행에 대한 경합이 심한 도메인에서는 MySQL InnoDB 행 잠금 데드락이 먼저 발생해 낙관적 락의 효과가 반감된다.

비관적 락(SELECT FOR UPDATE)은 충돌 자체를 원천 차단하지만 락 대기(blocking) 비용으로 응답시간이 낙관적 락 대비 약 20~30배 느려졌다(2ms → 70ms). 데드락은 없지만 처리량(TPS)도 낮아진다. 경합이 심한 도메인에서는 데이터 정합성을, 경합이 드문 도메인에서는 성능을 우선시해 락 전략을 선택해야 한다.

또한 테스트 환경(H2)과 운영 환경(MySQL)의 동시성 동작이 다르다는 점을 반드시 인지해야 한다. H2에서 93% 성공하던 낙관적 락이 MySQL에서는 63%로 낮아졌다. 부하 테스트는 반드시 실제 운영 DB와 동일한 환경에서 진행해야 신뢰할 수 있다.
